# Minimal working methodology (1.0 preview)

This document is the 1.0 preview of a working methodology that a project activates explicitly. Its effect has not yet been verified, and its structure may change. It is not a port of, or an equivalent replacement for, the whole of the earlier public methodology (v0.2).

Follow the current host's permissions and the project's product requirements, approval conditions, write scope, and required verification first. However, the three requirements in `Human judgment` below cannot be waived by host or project rules. The methodology grants no new permissions, budget, or model calls. If a conflict cannot be resolved, stop the activation or the edit and record the evidence.

1. Confirm the task goal, the current code, and the information, execution tools, and verification environment you need. Do not wait for a failure when you already know a condition is needed.
2. Before changing anything, connect each requirement's target and verification method to a short, observable list of files, symbols, and order. Reuse connections that an existing plan already makes; details follow `supports/ordered-changes.md`. This is the default support of the current preview; do not remove it because of a single success or a model name.
3. Implement within the allowed scope and actually run the checks the project defines. Do not reuse past results as a PASS for the current run.
4. Compare the requirements at the revision the project approved or designated as the baseline against the final change and check evidence. Also look for missing targets and for final verification that was narrowed or left gaps. The model's judgment of success and the actual adoption of the result are separate. Distinguish unverified, implementation defect, environment failure, and unknown cause.

Concrete work units and product facts are managed by the project. Do not require a new document or a separate plan file for every task. This methodology is not a security boundary or an automatic agent runner.

## Human judgment

1. When an unresolved question that needs human judgment arises, stop the work that depends on that judgment and ask a human. Work that does not depend on it may continue. Questions that need human judgment include at least: judgment points the project designates, actions outside the scope allowed by project settings or working instructions, requirement interpretations that diverge into two or more readings, and choices that change a settled decision or contract. If you are unsure whether judgment is needed, ask.
2. The project specifies the points where a human judges (for example, design-stage approval, merge, deployment) in its own settings or working instructions. The project decides which points, how many, and how the judgment is received.
3. The Agent does not create decisions a human did not make. A passing review, passing tests, a general instruction to proceed, or silence does not stand in for a human decision. A delegation that a human has recorded in project settings with its scope, date, and confirmer is a human decision within that scope. A general instruction to proceed without a scope is not a delegation. The Agent does not create, extend, or finalize delegations.

These three are the common minimum requirements. Host and project rules may make them stricter but may not waive them. On conflict, stop the work that depends on that judgment and ask a human. If the execution environment cannot ask a human, stop that work and record the question as unresolved.

## Application and improvement observation

The Agent doing the work leaves the links below in the project's existing work records. Reuse the issues, PRs, and handoff records the project already defines; do not assume a separate service or a dedicated ledger. The project's start, handoff, and closing procedures must consume this section. Do not claim automatic collection or behavioral compliance merely because documents were distributed or the copy's hashes matched.

The project defines one reference location for work records and the relation used to find earlier records. Record in one start source for the task the pinned commit or manifest hash, the document paths read, the applied interval, the retention location, and the planned supports. Later records may reference their own task's start source directly and omit copying the pinned information. When application information changes, mark the time of change, the new value, and the interval, and do not retroactively update earlier intervals. Do not substitute a name-only version or a run ID that cannot be resolved later for the source. If earlier observations are used, record the relation between that source and this task and the action chosen; if there are none or they could not be found, record that state.

| When | What to record |
| --- | --- |
| Start of application, before actual changes | Task/run identifier, the pinned version and documents read, the supports and interval to be applied, and the project location where observations are retained. If earlier observations exist, read the source and link the evidence and actions relevant to this task. If there are none or they cannot be retrieved, record that. |
| Handoff or interruption | Direct reference to the start source, current state, supports performed and observation evidence, uncollected items and why, and where the next owner should continue reading. Record in the existing record, as separate items, whether the source is accessible and whether it was actually read after the handoff. Do not reset to a new task or retroactively apply past intervals because the owner changed. |
| End of implementation and final close of the task | Direct reference to the start source, supports actually performed and differences from the plan, final requirement–verification results and gaps, observations and evidence of missed requirements, verification failures, rework, control triggers/false positives, and human intervention, available cost sources and their scope, collection gaps, and the next judgment under `adaptation.md`. If the same result is already in an existing record, reference it directly. Update the existing closing record or preserve the final state in a follow-up record, while keeping earlier failures and the target at that time distinct from the final correction. |

What may be omitted is a body copy of the same information. New failures, unmet requirements, narrowed verification, lost sources, and changes in the next judgment are not hidden behind a reference; surface them in the current summary. Do not read the absence of a record as no change, zero, or confirmed. When the task changes, keep its start record distinct; reuse of an earlier or parent task's actual-reading record follows project rules and states the source and relation. Do not exempt a new task from reading or let it inherit an earlier task's cost or model observations. Do not require a separate shared ledger, a copy, or a full re-query of unrelated past records.

Observations distinguish confirmed facts, causal hypotheses, and non-observation. `not observed` means the event was not found within the checked scope, not that it was zero across the whole task. If there is no source, record `not collected` and the reason. Do not omit the remaining observations because one metric is missing. Use pinned commits or source IDs/links for requirements, checks, changes, and reviews; for mutable records, record the time checked and the target revision.

Distinguish the source type of an observation (tool output, separate review, Agent self-report, and so on). Identify a mutable record without a revision by its source ID and update time; if there is no update time either, record the limitation that changes cannot be verified. Several unobserved items may be grouped on one line when they share the same reason and scope. Do not require a blank table per item or an exhaustive survey.

For models, distinguish requested settings from information actually provided, and the source of each. In work records such as the closing summary, record the confirmed requested model and requested reasoning setting and the source of each. Do not drop a confirmed requested value or change it to `unconfirmed` because the actually provided model or reasoning setting could not be confirmed; mark only the unconfirmed provided values as `unconfirmed`. When recording a self-report or a display name, label it with that source and do not rewrite it as a requested or provided value. Record role and agent identifiers separately and do not use them in place of model values. Use cost only when the unit, run scope, and overlap of the host-provided observation are confirmed. Do not double-count cumulative and interval values, root and worker, or totals and their cache/reasoning sub-items. Do not estimate costs that were not provided, provided models, or human time. If the project already has instrumentation labels, do not change their source to other data. Check source and collectability in the current interval; if the collection limits are the same as in the start record, items with the same reason and scope may be grouped on one line by reference. State new values, scopes, and changed limits explicitly.

Before cleaning up the work folder, retain records and the necessary non-sensitive evidence in a location the project can query again, and re-query it. Do not collect conversation transcripts, quotes, reconstructable summaries, secrets, or product user data. Do not create a new storage location to retain prohibited material. If the start source disappears or differs from the version checked, do not keep the application confirmed by reference alone. Record the application information that can be checked directly now and the scope of the loss in the existing record, and leave earlier intervals unconfirmed. State lost sources and failed retrievals explicitly, and do not restore verified facts from summaries or estimates.

Application state and collection state are separate. Check version reading, support execution, observation recording, source re-query, and hand-off to the next judgment individually, and surface unconfirmed steps. If introduced mid-task, record only the later interval as partial application. Collection gaps are a limit of methodology evaluation, not a new gate for project completion or an approval waiver.

### Recording problems found and connecting to the project

Record an event in the existing work record only when an actual problem is found during execution, verification, or review, such as a missed requirement, a verification gap, a failure, or unnecessary rework. Do not automatically count expected failing tests or normal design exploration as problems. Do not add rows for normal steps, empty event lists, `no problems` reports, or exhaustive execution traces. The existing start, handoff, and closing obligations remain; this section adds only conditional problem recording. Apply the same principle to tasks without a separate design document (for example, small tasks), and do not create a design document just to record.

The project adapter connects **the task identification method, the work-record reference location (including the start record) and how to find earlier records, the problem record location, the closing summary location, the final close decision, and the allowed query/write means and scope** to existing settings or working instructions. It does not require a separate configuration file or service. Closing tags, comment markers, and host APIs are not common required values.

| Connection example | Problem record and summary | Close and query |
| --- | --- | --- |
| Issue tracker | Existing task activity/comments → task closing summary | The project's final state and allowed API/CLI |
| Local documents | Events section of the existing task document → closing summary in the same document | Completion marker defined by the project and file path/item references |

If there is no existing record location at all, the project first designates a minimal per-task record location, and the event record is created only when the first problem is found. If there is no location or permission, or the write fails, pass the retention failure and checkable evidence through the existing handoff/closing path and do not report it as a successful record. Do not work around it by posting to an arbitrary service or a new central ledger.

An event records, briefly: an existing ID/source reference that distinguishes the task and the event, the stage where it occurred (unknown allowed) and the stage where it was found, the role/agent identifier that performed the work and who found it, the confirmable model and reasoning setting and their source, the problem observed and its evidence, and the action and result. Settings distinguish requested values from metadata the host actually provided; unprovided values are `unconfirmed`. Do not self-estimate model names or reasoning settings, or substitute the finder's model for the performer's. Separate observed facts from causal hypotheses and unknown attribution, and do not record conversation or reasoning transcripts.

A subagent includes an event or a source reference in its existing return only when there is a problem, and the parent owner retains it. Handoffs, retries, fixes, and closing summaries of the same event keep the source reference linked and do not overwrite the first failure with the final success. Do not merge distinct occurrences into one event because they are of the same type.

The closing owner gathers the key facts, owner metadata, actions/results, and source references of recorded events into the existing closing summary. Do not leave only links, so that events are visible even to adapters that query only the summary. Before deleting the work folder or a temporary design document, move the necessary facts to a durable retention location. An approved design document does not need to be edited into an event ledger. Something found after close is linked to the earlier task by the follow-up task that found it, and is not backdated as if observed at the earlier close.

What is publicly distributed is this contract and the adapter's way of connecting. Do not automatically post project events, model usage records, or evidence to a common repository or send them externally. When sharing generalized common improvement candidates, follow the project's permissions and information-disclosure scope.
