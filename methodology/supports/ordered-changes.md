# Default support: ordered change list

Before editing, write the files and symbols to change and the order of changes as a short, observable list in the response or the planning tool. The project's permissions, scope, and verification conditions remain separate.

Compare the requirements and completion criteria within this task's scope at the revision the project approved or designated as the baseline. Use existing IDs or document sections and items to connect each requirement's target, conditions, expected result, and verification method to the list. If an existing plan or verification spec already makes the same connection, reference its location and fill in only what is missing. Keep the files, symbols, and order; one sentence is enough for a simple change. Example: `baseline §2 save-button disabled condition → fix button state calculation → check clickability when the condition is met / not met`.

For requirements that span multiple entry points, actors, or states, distinguish the targets. Normal, failure, cancellation, and similar paths are covered where the original requirement or the change's impact applies, not to fill a fixed number of cases. If interpretations of a requirement diverge or the baseline source cannot be found, leave it open / correspondence unconfirmed, and progress that depends on that judgment stops and asks a human under `core.md` `Human judgment` 1. Do not complete the list by guessing requirements.

In the existing implementation review and closing check, compare baseline requirements → actual changes → the final candidate's check results and unconfirmed scope. Check not only the filled-in list but also connections missing from the baseline requirements. Do not substitute agreement among the latest documents edited during implementation for meeting the baseline, and do not relax requirements to match the implementation. Use methods the project allows, such as automated tests, direct observation, and code comparison; do not substitute test names or CI success alone for meeting a requirement. Reused results state the target and input scope and the fact of reuse, and are not reported as a new run.

If tests are removed, assertions weakened, runs excluded, or verification targets changed, re-judge the final evidence for the affected requirement. Surface the substitute evidence and remaining gaps in the existing closing summary; changes to required verification follow project permissions. For example, if only one of two entry points was checked, or a check was removed in the final candidate, do not write that the whole requirement is met.

Do not count the existence of the list as success in implementation quality. Do not require new IDs, separate plan files, a particular table format, separate retention of the list, or disclosure of internal reasoning. Do not add new review rounds or approval steps. When re-evaluating the support's effect, keep the common controls and vary only whether the list is required, and also observe voluntary list writing. Do not add results from versions with different list contents into the same support condition.

The current default is kept because the evidence for removing it is insufficient. Evaluation so far has been limited in scope (its evidence is not published) and does not support changing the default for the whole methodology or for other models or tasks.
