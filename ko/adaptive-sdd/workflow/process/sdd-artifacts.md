# SDD 작업 문서

Medium·Large의 해당 문서를 작성·수정할 때 필요한 절만 읽는다. Trivial·Small 및 Epic 관리 문서 자체에는 SDD 디렉터리를 요구하지 않는다. 문서 역할·수명은 [sdd-workflow](sdd-workflow.md#문서-역할), 검증 대응과 실행은 [verification](verification.md)이 원본이다.

| --- | --- |
| 폴더·작업 인덱스 | [구조](#sdd-작업-문서-구조), [README](#readmemd) |
| 현재 동작·조사 근거 | [AS-IS](#01-as-ismd) |
| 목표 동작·결정·완료 기준 | [TO-BE](#02-to-bemd) |

## SDD 작업 문서 구조

Medium 이상에서 다음 구조를 사용한다. 새로 시작하는 SDD 작업부터 적용하며, 이미 진행 중인 작업과 종료된 작업에는 소급 적용하지 않는다. 이 규칙만으로 기존 설계를 재작성하지 않는다.

```text
docs/sdd/{feature}/
  README.md
  01-as-is.md
  02-to-be.md
  change-plans/{ID}.md
```

필요한 경우에만 `backlog/{ID}.md`를 추가한다. `{feature}`는 kebab-case, `{ID}`는 Issue 안에서 중복되지 않는 대문자 prefix + 번호를 사용한다.

각 문서의 필수 내용은 다음과 같다.

사람용 현황·계획에는 [사람용 문서의 시각적 작성](agent-instruction-policy.md#사람용-문서의-시각적-작성)을 적용한다. 현재 모습과 변화·선택을 먼저 보여주고 Agent 실행 세부는 분리한다. 한 문장으로 충분한 변경은 그 문장으로 설명하며 그림 개수를 채우지 않는다. 표현 선택에 예시가 필요하면 [작성 예시](visual-writing-examples.md)만 참고한다. 이 연결은 문서 구조·승인 권한·review 회차를 바꾸거나 전체 가이드의 선행 로딩을 요구하지 않는다.

### `README.md`

- Issue 번호
- Priority
- grade
- 수정 허용/금지 경로
- 연결된 business/architecture 문서

### `01-as-is.md`

- 문제 정의·원인 모델·범위/경계와 설계에 영향을 주는 핵심 사실·위험을 먼저 짧게 제시
- 현황 이해에 필요한 소유·연결·흐름·상태는 관계도나 작은 표로 먼저 보여주고 사실·가설·미조사를 구별. 단순 변경은 한 문장 허용
- 현재 동작과 확인하지 못한 사실을 구분한 Agent evidence
- 확인한 코드 경로와 심볼
- 재현 또는 검증 근거
- 문서와 코드가 다르면 drift 항목

작성 순서는 문제 → 현재 관계·동작 → 사실/가설/미조사 → 직접 근거로 잡는다. 구체적인 표현이 필요할 때만 W의 [AS-IS 합성 예시](visual-writing-examples.md#sdd-as-is)를 참고한다. 예시의 가상 사실을 실제 제품 근거로 사용하지 않는다.

#### 판단에 필요한 조사

사람의 선택이나 다음 작업의 전제를 좌우하는 항목에만 아래 조사를 적용한다. 상위 분석의 유효한 근거를 재사용하며 전수 이력 조사나 별도 분석 문서를 요구하지 않는다.

| 판단 상황 | 확인할 근거 |
| --- | --- |
| 기존 구현을 기준으로 이관·통합 | 이름과 실제 식별자, 활성 진입점, 확인한 revision 및 최근 운영 근거의 대응. 코드상 활성과 실제 운영 사용을 구분 |
| 구현 차이·비활성화 이유가 선택에 영향 | 관련 도입/변경 이력·티켓과 의도 근거의 유무. 작성자·시점만으로 의도를 확정하지 않음 |
| 외부 라이브러리·프레임워크 동작에 의존 | 실제 의존 버전의 소스·배포물/bytecode·공식 문서 또는 허용된 최소 실행. 다른 버전의 설명을 적용 근거로 사용하지 않음 |
| 데이터·로그·endpoint·전환 방식을 변경 | 직접 연결된 외부 호출자·운영 소비자·관측 방식과 그 정보의 원천·확인 시점. 코드에 없다는 이유로 소비자가 없다고 추정하지 않음 |

사람에게 선택을 묻기 전에 범위 안에서 확인 가능한 사실은 먼저 확인한다. 남은 불확실성은 확인한 근거·접근 실패·실행 필요·외부 확인 필요와 그 결론이 필요한 단계를 함께 적는다. 탐색을 무한 반복하거나 권한 밖 운영 조회를 하지 않고, 필요한 외부 사실만 사람에게 요청한다. 위험에는 발생 조건과 실제 관찰 범위를 적으며 근거 없이 빈도를 추정하지 않는다. 운영 내용은 P의 기존 문서/작업 기록에서 관리하고 공통 사본에 넣지 않는다.

기준으로 지정한 구현이 비활성이라는 근거 등 요구 전제와 모순되는 사실은 일반 차이가 아니라 **전제 충돌**로 보고한다. 확정 결정 변경은 사람 판단 규칙에 따르고, 그 전제에 의존하는 설계·구현만 멈춘다. 무관한 조사까지 일괄 중단하지 않는다. 사람 질문에는 사람이 사용하는 식별자와 코드 이름의 대응을 함께 제시한다.

### `02-to-be.md`

Human Decision Contract다. Issue의 목표·경계와 상위 contract 안에서 제품·설계 결정의 기준이 되며, 이들을 독자적으로 변경하지 않는다.

- 현재 문제와 AS-IS → TO-BE 동작 변화. 정책·선택지는 비교표, 소유·경계는 관계도/경계 표, 흐름·상태는 다이어그램/상태표 등 이해에 필요한 표현을 먼저 둔다. 단순 변경은 한 문장 허용
- 변경하지 않을 동작, 실패/오류 시 동작, 명시적인 데이터/상태 정의
- Decision별 `D-xxx`, 선택, 선택 이유, 실제 대안과 trade-off, 주요 비용/위험, 채택하면 생기는 의미
- Acceptance Criteria별 Verification Strategy. 실행 세부는 해당 change-plan을 참조한다.

AS-IS에서 미확인으로 남긴 외부 동작을 설계 사실로 확정하지 않는다. 설계 결정을 좌우하는 전제는 위 조사 근거로 확인하거나 [미결 사항과 단계별 의존성](sdd-workflow.md#미결-사항과-단계별-의존성)에 따라 확인 담당·필요 시점을 연결한다. 실행으로만 확인할 수 있는 전제는 해당 검증/구현 인계에 남기고, 전제에 의존하는 실행 전에 확인한다.

클래스/메서드/line evidence는 최소화한다. 중요한 제품·설계 결정을 Agent spec에만 숨기지 않는다. Human-facing Decision이 짧은 리뷰 세션에서 이해하기 어려울 만큼 많으면 issue/plan 분리를 검토하되 고정 개수 상한이나 추가 taxonomy는 만들지 않는다.

작성 순서는 변화 → 선택과 이유·비용 → 유지할 경계와 실패·미결 → 완료 기준과 확인 방법으로 잡는다. 필요한 경우만 [TO-BE 합성 예시](visual-writing-examples.md#sdd-to-be)를 참고한다. 위 현황·계획 예시의 전체 선행 로딩이나 새 산출물은 요구하지 않으며, 실행 세부는 기존 change-plan의 해당 절로 연결한다.

### `change-plans/{ID}.md`

Agent Execution Spec이다. Human Decision의 rationale을 다시 서술하지 않고 적용하는 `D-xxx`를 참조한다. `02-to-be.md`와 경쟁하는 설계 권위를 만들지 않는다.

- target file/symbol과 직접 caller/callee, 필요한 코드 근거
- 변경 내용·구현 순서·보존할 invariant, 해당하는 schema/migration
- test case·검증 명령·실행 evidence
- 롤백 또는 실패 시 확인 지점

적용할 P 컨벤션의 문서·절·revision 또는 확인 시점을 연결하고, 지시한 구조가 그 기준과 다른 경우 이유와 필요한 예외 결정 근거를 적는다. 기존에 허용된 여러 스타일 중 하나를 고른 것을 나중의 선호만으로 위반 처리하지 않는다. 새 스타일을 공통 규칙으로 만들지 않으며 선언된 기준이 없다는 이유로 별도 컨벤션 문서나 승인 단계를 강제하지 않는다. 확인되지 않은 기준은 인계에 드러내고 실제 지시 충돌만 기존 권한 규칙으로 해결한다.

`관련 파일`, `필요한 부분`, `적절한 처리`처럼 정확한 대상을 특정하지 않는 문장을 change plan에 쓰지 않는다.

## 계획 정정과 정책 전환

구현·검증 중 계획의 전제가 틀렸거나, 진행 중 작업에 적용할 프로젝트 정책이 바뀌면 다음 경로로 현재 지시를 정정한다. Small 이하는 Issue의 계획·기록을 사용하며 SDD나 별도 전환 문서를 만들지 않는다. 검토한 PLAN이라는 이유로 틀린 지시를 유지하거나 SUMMARY에만 차이를 숨기지 않는다.

1. 발견 근거와 영향을 받는 전제·Decision·계약·검증을 특정하고, 그 전제에 의존하는 편집·실행만 중단한다. 필요한 사실 조사와 독립적인 작업은 계속할 수 있다. 기존 허용 경계 밖 임시 테스트 작성도 자동 허용되지 않는다.
2. 확정 결정·제품 의미·범위·권한을 바꾸면 기존 사람 판단 규칙을 적용한다. 이미 내려진 결정이나 유효한 위임을 근거로 사용할 수 있으며 단순 사실 정정에 새 승인을 만들지 않는다. 위임 밖의 대안을 구현자가 임의로 선택하지 않는다.
3. 현재 Issue와 해당 AS-IS/TO-BE/change-plan의 잘못된 지시를 수정하고, 기존 기록에 이전 revision·대체한 문장/항목·변경 이유·근거와 결정 참조를 남긴다. 원래 revision은 이력으로 보존한다. 원문을 즉시 수정할 수 없다면 연결된 보정 문서/기록에 대체 대상과 새 지시를 명시하고 현재 계획의 진입점에서 이를 발견할 수 있게 한다. 그 연결을 권한·동시성 문제로 만들 수 없으면 영향 작업은 재개하지 않는다. 두 지시 중 무엇이 현재인지 구현자에게 추정시키지 않는다.
4. 정책 전환은 적용할 Issue·phase·시점과 대체되는 기존 정책을 기록한다. 활성 담당·실행 중 리뷰·미커밋 변경·최근 작업 기록을 확인하고 적용 구간을 조율한다. 이전 실행·검토는 당시 정책과 target의 기록으로 보존한다. 단순 문서 위치 이동은 의미 변경과 구분하며 이미 진행한 작업을 자동 초기화하지 않는다.
5. 현재 grade의 self/required review와 [의미·영향별 재검토](design-review.md#의미영향에-따른-설계-재검토)를 적용한다. 기존 검토·검증 중 무효화된 근거와 유지 가능한 근거를 구분한다. 새 SHA나 정책 변경이라는 사실만으로 전체 A/B를 반복하지 않으며, 중요한 의미 변경을 문서 정정이라고 축소하지 않는다. 검증 입력이 바뀌면 [PASS 유효성](verification.md#검증-시퀀싱과-pass-유효성)에 따라 해당 검증을 갱신한다.
6. 필요한 current-target 근거를 확보한 뒤 Issue·계획·Execution Packet의 참조와 적용 정책을 맞추고 해당 담당에게 인계해 재개한다. 종료 시에는 정정된 계획·실제 구현·검증의 일치를 확인한다.

### Bounded trade-off capture

Issue, 선언한 기준 revision의 AS-IS, direct dependency를 확인하는 과정에서 실제 경쟁 선택지가 둘 이상 드러난 경우에만 선택, 대안, 선택 이유, 감수 비용을 짧게 기록한다. Medium 이상에서 중요한 제품·설계 trade-off는 `02-to-be.md`의 Decision에 두고 change-plan은 그 ID를 참조한다. Trivial/Small은 Issue를 사용하며 별도 trade-off 문서를 만들지 않는다.

경쟁 선택지를 찾기 위한 repository-wide 탐색이나 별도 brainstorming은 하지 않는다. 재검토 조건도 이미 명확한 trigger가 있을 때만 기록한다.
