# 공통 설계 의사결정 리뷰 형식

이 형식은 프로젝트가 review topic 작성을 요구하는 변경에 적용한다. 발동 조건과 실제 기록은 프로젝트가 소유한다. 기존 SDD required review를 대신하거나 독립 reviewer/승인 횟수를 자동 추가하지 않는다.

## topic 구조

```text
docs/reviews/
  NNN-<slug>/
    proposal.md
    review-<agent>.md
    decision.md
  _templates/
```

- `NNN`은 기존 가장 큰 번호 + 1의 세 자리 숫자다.
- `slug`는 영문 소문자와 `-`만 사용한다.
- `proposal.md`는 한 topic에 하나만 둔다.
- 각 reviewer는 `review-<agent>.md` 자기 파일만 작성한다.
- `decision.md`는 최종 결정 후 하나만 작성한다.

다른 agent의 `review-*.md` 본문을 수정하지 않는다. 반박이나 추가 근거는 자기 review 파일에 적는다.

## 상태

허용 상태는 다음 다섯 값만 사용한다.

```text
제안 → 리뷰중 → 결정됨
             ├→ 보류
             └→ 반려
```

`proposal.md` 헤더의 상태가 해당 topic의 상태 기준이다.

- proposal 작성 직후: `제안`
- 첫 review 요청 시: `리뷰중`
- decision 작성 시: `결정됨`, `보류`, `반려` 중 하나

`docs/reviews/README.md`의 링크 목록은 탐색용이다. 현재 제품 동작이나 구현 상태를 이 인덱스 표로 판단하지 않는다.

## proposal 필수 내용

사람이 읽는 proposal/review/decision에는 [사람용 문서의 시각적 작성](../agent-instruction-policy.md#사람용-문서의-시각적-작성)을 적용한다. 제안·결정의 핵심 변화와 선택을 상세 근거보다 먼저 보여준다. 정책·전후 차이는 비교표, 소유·경계는 관계도/경계 표, 순서·상태는 흐름/상태 표현을 필요한 경우 선택한다. 단순한 주제는 한 문장으로 충분하며 고정 그림 수를 요구하지 않는다.

proposal에는 다음을 포함한다.

1. 문제
2. 변경하려는 현재 규칙/contract
3. 선택지 2개 이상 또는 단일 선택지만 가능한 이유
4. 각 선택지의 장점·위험·비용
5. 선택하지 않을 범위
6. 결정이 필요한 질문
7. 코드/문서 근거

`더 좋아 보임`, `확장성이 좋음`, `유연함`처럼 측정 기준이 없는 표현만으로 선택지를 평가하지 않는다. 어떤 호출 경로, 비용, 실패 모드, 유지보수 경계가 달라지는지 적는다.

## review 규칙

review의 각 지적에는 다음을 적는다.

- 심각도: `치명`, `중요`, `제안`
- 근거: 실제 파일·심볼·문서 rule ID
- 상태: `확인됨` 또는 `추정`
- 영향: 어떤 요구사항/비용/장애로 이어지는지

실행하지 않은 검증은 `확인됨`으로 쓰지 않는다.

같은 review에서 첫 설명으로 변화·선택이 드러나는지, 그림·표의 조건·실패·미결이 본문과 같은지 확인한다. 의미 차이는 기존 지적·해결 절차로 다루며 새 승인이나 reviewer 회차를 만들지 않는다. 그림 유무·개수 자체를 판정 근거로 삼지 않는다.

외부 모델 가격이나 API 정책을 근거로 사용하면 확인한 출처와 확인 날짜를 기록한다. 기억만으로 단가를 적지 않는다.

## decision 규칙

`decision.md`는 다음을 포함한다.

1. 채택안
2. 채택 이유
3. 채택하지 않은 안과 이유
4. 변경되는 business rule/contract
5. 후속 Issue
6. 적용 시점

결정으로 `docs/domains/**`의 current business rule이 바뀌면 **결정만 기록하고 끝내지 않는다.** 구현 완료 작업에서 최종 코드와 business 문서를 함께 갱신한다.

과거 decision은 나중에 다른 선택으로 바뀌어도 삭제하거나 새 결론으로 덮어쓰지 않는다. 새 review topic에서 이전 decision을 참조한다.
