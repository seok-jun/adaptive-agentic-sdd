# 기본 지원: 변경 순서 목록

편집하기 전에 변경할 파일·심볼과 변경 순서를 응답 또는 계획 도구에 관찰 가능한 짧은 목록으로 작성한다. 프로젝트의 권한·범위·검증 조건은 별도로 유지한다.

이번 작업 범위의 요구·완료 기준을 프로젝트가 승인하거나 기준으로 지정한 revision에서 대조한다. 기존 ID나 문서의 절·항목을 사용해 요구의 적용 대상·조건·기대 결과와 확인 방법을 목록에 연결한다. 기존 계획·검증 명세에 같은 연결이 있으면 그 위치를 참조하고 부족한 부분만 보완한다. 파일·심볼·순서는 유지하며 단순 변경은 한 문장으로 충분하다. 예: `기준 §2의 저장 버튼 비활성 조건 → 버튼 상태 계산 수정 → 조건 충족/미충족 때의 클릭 가능 여부 확인`.

복수 진입점·주체·상태에 걸친 요구는 적용 대상을 구별한다. 정상·실패·취소 등은 원 요구나 변경 영향이 있는 경로를 다루며 정해진 경우의 수를 채우지 않는다. 요구 해석이 갈리거나 기준 원본을 찾지 못하면 미결·대응 미확인으로 남기고, 그 판단에 의존하는 진행은 `core.md` `사람 판단` 1에 따라 멈추고 묻는다. 요구를 추정해 목록을 완성하지 않는다.

기존 구현 리뷰와 종료 확인에서 기준 요구 → 실제 변경 → 최종 후보의 확인 결과·미확인 범위를 대조한다. 채워진 목록뿐 아니라 기준 요구에서 빠진 연결도 확인한다. 구현 중 수정한 최신 문서끼리의 일치로 기준 충족을 대신하거나 요구를 완화해 구현과 맞추지 않는다. 자동 테스트·직접 관찰·코드 대조 등 프로젝트가 허용한 방법을 쓰고, 테스트 이름이나 CI 성공만으로 요구 충족을 대신하지 않는다. 재사용 결과는 대상·입력 범위와 재사용 사실을 표시하며 새 실행으로 보고하지 않는다.

테스트 제거·단언 약화·실행 제외·검증 대상 변경이 있으면 해당 요구의 최종 증거를 다시 판정한다. 대체 근거와 남은 공백은 기존 종료 요약에 드러내고 필수 검증 변경은 프로젝트 권한을 따른다. 예를 들어 두 진입점 중 하나만 확인했거나 최종 후보에서 검사가 제거됐다면 전체 요구 충족으로 쓰지 않는다.

목록의 존재를 구현 품질의 성공으로 세지 않는다. 새 ID·별도 계획 파일·특정 표 형식·목록의 별도 보존·내부 사고의 공개는 요구하지 않는다. 새 리뷰 회차나 승인 단계를 추가하지 않는다. 지원 효과를 재평가할 때는 공통 통제를 보존하고 목록 요구 유무만 바꾸며, 자발적 목록 작성도 관찰한다. 목록 내용이 다른 버전의 결과를 같은 지원 조건으로 합산하지 않는다.

현재 기본값을 유지하는 이유는 제거의 근거가 부족하기 때문이다. 지금까지의 평가는 범위가 제한됐고(근거는 공개하지 않았다), 전체 방법론이나 다른 모델·작업의 기본값 변경을 뒷받침하지 못한다.
