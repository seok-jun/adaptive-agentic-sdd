# Application and improvement observations

Observations are linked to the existing start, handoff, SUMMARY and closing records. Read only the content for the points below that apply, and reuse check results for the same run and version. Observation gaps do not create a new gate on existing product completion.

| When it applies | Section to read |
| --- | --- |
| Start, handoff and closing of every execution grade | The row for the current point in [Application and improvement observation](#methodology-application-and-improvement-observations) and the common interpretation rules |
| Writing a SUMMARY | [Recording the authoring model](#recording-the-authoring-model), the lookup location for the current host |
| Finding an actual problem, handing off an incident, gathering at closing | [Recording problems found and linking them to closure](#recording-problems-found-and-linking-them-to-closure) |
| Product completion and cleanup | [Closing observation check](#closing-observation-check) |
| When token diagnostic is ENABLED | The separate [token-diagnostic](token-diagnostic.md) |

General observations apply whether or not there is a token tracker. Problem incidents are recorded only when found, and token checkpoints follow their own activation condition.

## Methodology application and improvement observations

New work in this project, after the existing claim and grade gates, checks the application scope of the pinned common bundle and the sections needed for the current step, and applies them. The project's approvals, write boundaries, verification and completion conditions take precedence. Do not declare execution or collection complete based only on whether a linked file exists or on reading documents.


Manual observation re-review is done only when a human requests it. This preview does not yet have a re-review skill, so follow `Using observations for the next judgment` in M's `adaptation.md`. For each improvement candidate, present its owning location and exact content; only after human confirmation, create it and then re-query it. Before confirmation, creation happens 0 times, and an analysis-only instruction forbids writes. This grants no permission to correct existing sources or to implement candidates automatically.

Reuse the same version already read in the same run. Do not make local absolute paths, installation of a specific CLI or a separate settings file mandatory. On a source lookup failure or pin mismatch, leave `application unconfirmed` with the reason, and do not substitute an arbitrary latest version. Continue the work that the existing product procedure allows, but do not count unconfirmed as a successful application. Do not implicitly change the version of work in progress; an introduction partway through is recorded as partial application for the later span only.

The current work Agent is responsible for collection, and the Issue comments of this project are the baseline preserved source; the PR's evidence is linked from that Issue. Do not create a separate file, central ledger or whole-session collector. Attach the content below briefly to the existing start, handoff and `[IMPLEMENTATION SUMMARY]` records. Fixed information may be left in one start source per task, and handoff and closing may reference that URL directly and omit copying the body of the same version, documents and supports. If the application information changes, state the time of change, the new value and the span, and do not retroactively update the earlier span. Items not observed may be grouped in one line with the same reason and scope; no exhaustive survey is required. Run this whether or not there is a cost tracker. Required verification remains. Reuse valid evidence already obtained for the same candidate and verification inputs. Keep detailed evidence in one place, and leave in reviews, the SUMMARY and the Epic only the needed results, gaps and problems found, with a source reference. Create additional tools or evidence files only when a required item is not satisfied by existing evidence.

| Point | Consumption and recording |
| --- | --- |
| Before the actual change | Issue/run, pinned revision/pin, documents read and lookup evidence, applied supports and span, preservation location. First read the earlier observations in the current Issue's dependencies and linked PRs. If there is no reference, check up to one recently closed task within the same change boundary and leave the related source URL or `no related record/lookup unavailable`. Do not search the whole history. |
| Handoff, external interruption | Pass in the existing handoff the start comment URL, the actual supports, current observations/sources, reasons for non-collection, the next action and where to resume. Do not treat a change of owner as a new START. Distinguish whether a source is accessible from whether it was actually read after the handoff. |
| End of implementation | Reference the start source and existing results directly, and leave in the existing SUMMARY: the difference between actual supports and the plan; the final requirement-verification results and gaps; the scope checked and evidence for missed requirements, failures, rework, control triggers/false positives and human intervention; the source and scope of costs, or the reason they were not collected; the one line from `Recording the authoring model` below; and the next judgment. Link `keep support/adjust within scope/separate change candidate/insufficient data` with its evidence. If a known follow-up Issue already exists, link its reference; do not automatically create a new Issue or model run. |
| Before final closing and cleanup | Re-query the start record, the SUMMARY and the needed non-sensitive sources, and leave the URL, time of check, target revision (for comments, the ID and updated_at) and lookup status. Facts found after closing are recorded by the follow-up work that found them, linking the earlier source. |

What may be omitted is a copy of the body of the same information. New failures, unmet requirements, reduced verification, lost sources and changes to the next judgment are made visible in the current SUMMARY. Do not interpret the absence of a record as no change, zero cases or check complete. If the start source is lost or differs from the version checked, leave the application information currently checked directly and the scope of the loss, and leave the past span as unconfirmed. New work uses its own start source; it does not use an earlier task's reference as an exemption from reading, and does not inherit cost or model observations. Check the cost source and whether collection is possible in the current span, and reference only identical limitations as a group. State new values, scopes and limitations.

Observation items distinguish the source type, such as `tool/CI evidence`, `separate review` or `Agent self-report`. For `not observed`, write the span and evidence checked; if there is no source or observation, it is `not collected`. Do not record evaluations that need causal interpretation, such as false positives or preventive effects, as confirmed values without evidence. Distinguish the model settings requested from the metadata actually provided, and do not put figures from another source into existing TOKEN markers. Do not record conversation/reasoning transcripts or summaries from which they could be reconstructed.

That an input or execution evidence does not mention a particular item does not mean that item was checked. When there is only evidence of verification failures/fixes, do not fill in human intervention, false positives and missed requirements as `not observed`; group them as `not collected — no confirming evidence`. Even if a closing judgment candidate was left, if no separate follow-up work consumed it, state `follow-up consumption unverified`.

The Agent of the next related work compares the earlier source's methodology version, product revision and open/follow-up status with the current work, and leaves in the start record the reason for use/defer/not related. If there is no source, do not restore verified input from a past summary alone. Product-specific facts stay in the product; common methodology change candidates are presented as generalized requirements with a source reference, without duplicating product facts. One collection and one follow-up consumption, a synthetic evaluation, and a causal effect of a model/methodology are different claims.

Collection gaps and missing external documents are not a new gate on existing product completion. Implementation and verification failures are handled by the existing rules. An Issue that changes this linkage itself must verify the linkage acceptance criteria it specifies. If existing records provide the same linkage, or if the recording burden or repeated non-use is confirmed, review keeping or reducing the duplicate records within existing permissions.

### Recording the authoring model

The `[IMPLEMENTATION SUMMARY]` of every grade leaves one line with the model of the Agent that wrote the SUMMARY.

```text
Model: requested <model>/<reasoning> (source: session record|config file|Human-specified) · actually served <value|unconfirmed>
```

- Role or actor identifiers (for example `codex-root`, `Codex`) are not model values.
- Even if the actually served value is `unconfirmed`, do not omit the requested value and source that were confirmed. If neither the requested value nor the actually served value can be confirmed, leave each as `unconfirmed`. Do not self-estimate the model name or reasoning setting.
- Do not substitute the value of earlier work, another actor or a reviewer. If the model changes during the work, record the time of change and the new value by span.
- A missing model line or `unconfirmed` is not a completion gate.

The lookup location for each host is as follows. Session records also contain the conversation body, so extract only the field in question and do not read or print whole lines.

- Codex: `model`/`effort` in the `turn_context` entries of the current session record (default location `~/.codex/sessions/**/rollout-*.jsonl`) are the requested values. If the current session record cannot be identified, leave `model`/`model_reasoning_effort` from `~/.codex/config.toml` with source `config file`, and leave whether it matches the session as `unconfirmed`. This record has no model value actually served by the server, so actually served is `unconfirmed`.
- Claude Code: the assistant response `message.model` in the current session transcript (default location `~/.claude/projects/<project>/<session>.jsonl`) is the actually served value. If the requested reasoning setting cannot be confirmed from this record, leave it as `unconfirmed`.
- If the fields above are absent or the host is different, leave only the scope checked and leave the rest as `unconfirmed`. The existence of the fields above was confirmed on 2026-10-15 on one PC with one Codex session record and one Claude Code transcript each, and was not checked on other host versions or environments.

### Recording problems found and linking them to closure

This product consumes the common core's `Recording problems found and connecting to the project` as follows. Work is identified by Issue/run; the incident source is **the ordinary work comment on that Issue**, and the closing summary is the existing `[IMPLEMENTATION SUMMARY]`. Final closing, collection eligibility and lookup means follow the manual re-review contract above as is. GitHub comments and RELEASE/check are choices of the product adapter, not required formats of the common methodology.

- Record only when an actual problem is found, including in Trivial and Small. The targets are missed requirements, verification gaps, failures and unnecessary rework; expected negative tests and normal exploration are not tallied automatically. If there is no problem, do not create a new comment, incident section, empty list or normal-step row. Keep the existing start, SUMMARY and closing check, and do not create an SDD, extra comment tags or a separate ledger.
- The owner who found it leaves briefly in the existing work comment: **the incident reference, the phase where it occurred/was found, the performing role and identity and who found it, the model/reasoning settings that can be confirmed and their source, the problem observed and its evidence, and the action/result**. For a new comment, use its URL/ID after posting as the incident reference; if one comment holds several incidents, distinguish the items. Fixes and re-handoffs of the same incident reuse that reference. Distinguish the requested model value from the actual host metadata, and leave anything not provided as `unconfirmed`. Do not substitute the model of the reviewer who found it for the implementing model, and do not conclude that an unknown cause is a model defect.
- Workers/reviewers pass that information or a source reference in the existing result packet only when there is a problem. Writes to the Issue are gathered by the higher owner, and an identical incident already preserved is not duplicated in a new comment. On a recording permission or lookup/write failure, leave the preservation failure and the evidence that can be confirmed in the existing handoff/closing record, and do not save it around the failure to an arbitrary file or service. A recording failure by itself does not add to the existing completion gate.
- The closing owner follows the incident references left in the current work and gathers the key facts, owner metadata, evidence and action/result into the `Problems found` part of the SUMMARY. **Ordinary records may be excluded from re-review input, so leaving only a link is not enough.** If there are no incidents, do not create this part, and do not infer no problem/zero cases. For a resolved incident too, leave both the initial failure and the corrected result. If the source has disappeared, distinguish the remaining facts from the scope of the loss, and do not restore by guessing.
- Incidents that exist only in an SDD or a local worker result are preserved in the existing Issue before deletion or handoff. Do not modify a design document that passed review because of an incident record. Incidents found by CI/review after the PR are also updated in the same SUMMARY. Something found after final closing is linked to the earlier source in the record/SUMMARY of the follow-up work that found it; past RELEASE records or collection periods are not manipulated.

The improvement skill uses this SUMMARY and direct evidence to remove duplicates of the same incident and to examine repeated patterns by phase, role, model/reasoning setting and problem type. It distinguishes requested settings, actual metadata and unconfirmed, and does not turn counts into failure rates or model rankings. It does not automatically publish product incident sources to the common repository.

## Closing observation check

Distinguish product completion from local cleanup and ownership release. Confirmation of the actual merged PR and closed Issue and the `[PRODUCT COMPLETE]` format follow [finishing-issues](../skills/finishing-issues/SKILL.md#6-merge-confirmation-and-release). Before cleanup, re-query the start record, the SUMMARY and the needed sources from their durable preservation location, and update the final status and lookup results in the existing SUMMARY. State lookup failures, partial application and non-collection, and do not leave files that exist only in a local worktree as the only source.

An observation record check tool is not included in this preview. Leave one line `observation-check unavailable reason=not-shipped` in PRODUCT COMPLETE and continue. This result does not change release or closure and does not become `BLOCKED` or a stop condition.

- A normal single run records only the one result line above. Do not tailor records or run repeatedly to remove `missing`/`unavailable` or to obtain `confirmed`. Do not make re-runs mandatory or retry automatically.
- When re-running because of an actual input or environment change or a fix to a wrong execution order, first preserve the **initial original output** in the existing SUMMARY and briefly record what changed. If a re-run has already happened, leave the initial output obtained, the reason and the final output separately in the same SUMMARY. In PRODUCT COMPLETE, leave one line of the final output, whether there was a re-run and why, and the SUMMARY reference. Do not overwrite the initial result or create a separate log or central ledger.
- If the initial output was lost, leave `initial output unavailable` with the reason, and do not restore it by guessing. A re-run's `confirmed` is also a verdict on the record format, not independent evidence of compliance or effect. Results, re-runs and losses are not new blocking conditions on cleanup/release.
